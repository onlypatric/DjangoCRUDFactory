# Feature Request: Grouped Collection Actions With Per-Row Scoped ACL

## Summary

`CRUDFactory` should support collection endpoints that do **not** return one response DTO per model row, but instead return a **grouped / reduced payload** built from many rows.

The concrete use case is a monitoring/items endpoint that must:

- start from `Item` rows
- filter rows with normal queryset logic
- enforce scoped ACL on each individual item
- group the surviving rows by `Host.station`
- return a nested response tree

This is currently possible only with a custom DRF view or with a `CRUDFactory` custom action that still performs the core ACL filtering manually in the handler.

## Problem

Today `CRUDFactory` is optimized for this shape:

- `1 model instance -> 1 response dataclass`

This works well for:

- list endpoints
- detail endpoints
- typed nested dataclass responses
- aggregate stats
- filter / ordering metadata
- scoped ACL on one instance

But some read endpoints need this shape instead:

- `N model instances -> 1 grouped collection response`

Example:

- `Item` belongs to `Host`
- `Host` belongs to `Station`
- endpoint should return:
  - `Station`
  - nested `Host[]`
  - nested `Item[]`

Additionally, ACL is defined on the `Item` resource nodes:

- permission key: `app.monitoring.items.read`
- resource type: `monitoring_item`
- resource key: `monitoring_item:<itemid>`

So the endpoint must:

1. inspect all candidate `Item` rows
2. check item-level scoped ACL per row
3. discard unauthorized items
4. group authorized items by host/station
5. serialize the grouped structure

The current collection custom action API does not solve this cleanly because its ACL model expects one action-level resource reference, not row-by-row scoped filtering on the source queryset.

## Current Limitation

`CRUDFactory` currently supports collection custom actions like:

- handler input: `QuerySet[M]`
- handler output: one response dataclass

However:

- the action ACL check is performed once per action
- scoped collection action ACL requires one `acl_resource_ref_resolver`
- there is no first-class hook for:
  - filtering source rows by per-row scoped ACL
  - then reducing the authorized collection into a grouped response

This forces consumers to:

- bypass `CRUDFactory` for these endpoints, or
- use `CRUDFactory` only as a shell and still perform manual ACL filtering inside the action handler

## Proposed Feature

Add first-class support for **grouped collection actions**.

### Proposed API Shape

One possible API:

```python
from crudfactory import grouped_collection_action

grouped_collection_action(
    name="station_summary",
    input_dataclass=StationSummaryQuery,
    response_dataclass=StationSummaryCollectionResponse,
    handler=build_station_summary,
    acl_mode="filter-each-source-row",
    acl_permission="app.monitoring.items.read",
    acl_resource_ref_from_source_instance=lambda item: ACLResourceRef(
        resource_type="monitoring_item",
        resource_key=f"monitoring_item:{item.itemid}",
    ),
)
```

Or more explicitly:

```python
grouped_collection_action(
    name="station_summary",
    input_dataclass=StationSummaryQuery,
    response_dataclass=StationSummaryCollectionResponse,
    source_model=Item,
    source_queryset=item_queryset,
    source_acl=CollectionSourceACL(
        permission="app.monitoring.items.read",
        mode="scoped",
        resource_ref_from_instance=item_resource_ref,
        queryset_filter=filter_collection_for_acl,
    ),
    handler=group_items_by_station,
)
```

## Expected Behavior

The generated endpoint should:

1. build the source queryset
2. apply normal request filters / ordering if configured
3. apply per-row ACL filtering on the source collection
4. pass the authorized collection to the grouping handler
5. serialize the final grouped response dataclass

This would make grouped endpoints a first-class capability rather than an escape hatch.

## Response Contract Example

Example grouped response:

```python
@dataclass(frozen=True)
class StationSummaryItemResponse:
    id: int
    name: str
    units: str | None


@dataclass(frozen=True)
class StationSummaryHostResponse:
    id: int
    name: str
    items: list[StationSummaryItemResponse]


@dataclass(frozen=True)
class StationSummaryStationResponse:
    id: int
    name: str | None
    hosts: list[StationSummaryHostResponse]


@dataclass(frozen=True)
class StationSummaryCollectionResponse:
    stations: list[StationSummaryStationResponse]
```

This is different from a standard list endpoint because the response is a grouped wrapper, not a flat paginated list of `Item`.

## Why This Matters

This feature would let `CRUDFactory` cover a class of APIs that is common in operational dashboards:

- grouped monitoring summaries
- grouped devices by site
- grouped connectors by station
- grouped alarms by severity and plant
- grouped resources by parent entity

These endpoints are still:

- read-only
- typed
- deterministic
- compatible with dataclass response contracts

They just are not 1:1 row serializers.

## ACL Requirements

This feature is only really complete if it supports row-level ACL filtering on the source queryset.

Needed capability:

- source queryset ACL filtering before grouping

Not sufficient:

- one global ACL check for the whole action
- one scoped ACL resource ref for the whole action

The core need is:

- `authorized_source_rows = filter_collection_for_acl(source_queryset, actor, permission, resolver)`

followed by:

- `group(authorized_source_rows)`

## Suggested Implementation Direction

Add a new action type or extend collection actions with a `source_acl` concept.

### Option A

Introduce a new action constructor:

- `grouped_collection_action(...)`

### Option B

Extend `collection_action(...)` with optional source filtering hooks:

- `source_queryset`
- `source_acl_permission`
- `source_acl_mode`
- `source_acl_resource_ref_from_instance`
- `source_queryset_filter`

### Option C

Introduce a generic “collection transform pipeline”:

1. source queryset
2. filtering / ordering
3. ACL filter
4. transform / group
5. response serializer

This would likely be the most extensible design.

## Non-Goals

This request is **not** asking for:

- write support
- nested write orchestration
- automatic tree diffing
- generic recursive ACL inheritance

It is only about:

- read-only grouped collection responses
- with proper row-level scoped ACL on source rows

## Concrete Use Case

Monitoring items endpoint:

- source model: `Item`
- group by: `Host.station`
- filter condition:
  - `metadata.reporting.exclude_from_station_summary = false`
- ACL:
  - permission: `app.monitoring.items.read`
  - resource node: `monitoring_item:<itemid>`
- response:
  - `Station[] -> Host[] -> Item[]`

This is currently implementable outside `CRUDFactory`, but it is a strong candidate for first-class support because:

- the response is fully typed
- the source queryset is conventional
- the ACL model is conventional
- only the final reduction step is outside the current abstraction

## Recommendation

Add grouped collection support with source-row ACL filtering.

That would keep `CRUDFactory` aligned with the v3 direction:

- typed contracts
- concise endpoint definitions
- ACL integrated
- less custom DRF boilerplate
